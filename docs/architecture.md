# HouD2Launcher Architecture

## Boundaries

`core` contains Pydantic models, path safety, project/task/HIP services, and
environment resolution. It has no PySide6 or Houdini HOM imports.

`houdini` detects and validates installations, evaluates version compatibility,
builds process environments through the core resolver, and launches the exact
selected executable. The only HOM use is a script passed to `hython.exe` when a
valid blank HIP must be created.

`database` stores rebuildable indexes and histories. Project and task settings
remain canonical JSON next to project data.

`core.package_exchange` publishes immutable, checksum-verified Project and Task
snapshots to a user-selected shared folder. Imports always copy to a local
Project root, never overwrite an existing identity, and keep generated Cache
Roles in the separate Cache Exchange workflow.

`api` exposes an authenticated, localhost-only Cache Catalog while the Launcher
is running. Houdini receives its temporary URL and token through the child
process environment; HDA code never reads the Launcher SQLite database.

The top-level `houdini/python/houd2_cache` package is deliberately independent
of Pydantic and PySide6. It resolves the launch context, validates cache paths,
writes manifests and marker geometry, and supplies the two generated SOP HDAs.

`admin` is a separate localhost web application. It can inspect and repair the
SQLite index but cannot edit canonical Project or Task values directly.

`settings` creates credential-filtered export packages, computes import diffs,
validates the complete candidate model, creates a backup, and saves atomically.

`ui` contains all PySide6 widgets. Installation scans and potentially slow HIP
operations run on worker threads.

## Path Safety

All project paths are generated by `PathResolver`. User components are checked
for Windows-invalid characters and reserved names. Relative folder paths reject
absolute paths, empty segments, and `..`. Every resolved candidate is checked
against its allowed root before it is returned.

## Environment Priority

Environment layers are applied in this order:

1. Operating system
2. Launcher settings
3. Project settings
4. Task settings
5. One-time open overrides
6. Protected `HOUD2_*` internal variables

`HOUD2_API_TOKEN` is added only to the real subprocess environment after the
expression environment is built, so the Overview never exposes it.

## Cache Publishing

Cache Out writes into `v###.__writing__`, validates the generated geometry,
creates `cache_manifest.json` and `cache_marker.bgeo.sc`, then renames the
directory to `v###`. Cache In resolves a Catalog selection and reads only a
path contained by the selected source Task's `geo_cache` Role. Cache sync is an
explicit future API operation and never runs during SOP cooking.

Template references are expanded recursively. Cycles and unknown tokens fail the
launch before any process starts. Folder access uses `{role:folder_role}` rather
than physical folder names.

## Houdini Selection

The preferred installation is resolved in this order:

1. HIP metadata preference
2. Task recommendation
3. Project default
4. Launcher default
5. Newest enabled valid installation

Opening never uses Windows file association. The selected `houdini.exe` is
always passed directly to `subprocess.Popen`.
